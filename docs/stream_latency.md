# 실시간 센서 전송과 지연

카메라·LiDAR·IMU의 ROS 노드는 실행기 하나에 유지해 메시지마다 노드를 등록·해제하는
비용을 줄입니다. 영상 전송은 절대 시각 기준으로 간격을 잡아 타이머 지연이 매 프레임
누적되지 않게 하며, 실제 송신 시각에 따른 바이트 예산과 프레임 하나의 ACK 제한은
계속 지킵니다. 긴 지연 뒤 누락된 프레임을 몰아서 보내지 않습니다. 같은 출력 크기와
품질을 요구하는 시청자는 요청 해상도·FPS가 달라도 동일한 JPEG 결과를 공유합니다.
화면의 `수신 FPS`는 브라우저 수신 속도이며, ROS 원본 속도는 별도로 표시합니다.
카메라 전용 표시 정책은 최대 30 FPS를 허용하지만 실제 속도는 원본과 회선에 제한됩니다.
캡처 설정·원본 ROS 메시지·녹화 정책과 다른 센서의 전송 정책은 바꾸지 않습니다.

카메라·LiDAR·IMU·GPS는 WebSocket을 유지합니다. 화면이 받은 프레임의 ACK를
기다리는 동안 중간 센서 샘플을 쌓지 않고, ACK 이후 가장 최근 샘플을 선택합니다.
느린 연결에서 오래된 영상이 순서대로 밀려오는 현상을 막기 위한 구조입니다.
원본 ROS 메시지와 녹화 데이터에는 표시용 축소·프레임 생략을 적용하지 않습니다.

카메라는 JSON에 base64 영상을 넣는 대신 JPEG와 작은 메타데이터를 하나의
binary 메시지로 보냅니다. 같은 품질의 여러 시청자는 인코딩 결과를 공유하며,
JPEG 인코더를 기다리는 시청자도 차례가 오면 최신 원본을 다시 선택합니다.
새 ROS 영상이 오면 전송 루프를 깨워 기존 30 ms 폴링 대기를 줄였습니다.

대시보드 프록시는 인증된 WebSocket의 브라우저 방향과 센서 브리지 방향 소켓에
`TCP_NODELAY`를 적용합니다. JPEG의 마지막 작은 패킷이나 센서 ACK가 Nagle 알고리즘과
TCP 지연 ACK 때문에 대기하는 경우를 줄입니다. 일반 HTTP 소켓과 데이터 큐 정책은 유지합니다.

LiDAR는 각도·거리·반사값의 간단한 배열을 사용합니다. 표시용 ROS 구독 큐는
카메라·LiDAR·IMU·GPS 모두 최신 1개로 제한합니다. WebSocket 송신 버퍼도 제한하며,
카메라 한 프레임의 송신과 ACK는 합쳐서 최대 8초를 기다립니다. 매우 느린 연결에서도
화질을 유지하며 낮은 FPS로 갱신하기 위한 카메라 전용 한도입니다. 다른 센서 ACK의
2초 제한과 차량 STOP·센서 유효시간은 그대로입니다. 잘못되거나 이전 프레임의 ACK는
기한을 연장하지 않습니다. 카메라가 8초 안에도 응답하지 못하면 연결을 닫고 재시작을
기다립니다. 브라우저는 이 오류를 무한 재연결로 숨기지 않습니다.

IMU 전송은 송신·ACK에 걸린 시간을 다음 갱신 간격에서 빼도록 수정했습니다.
예를 들어 화면 주기가 100 ms인데 ACK에 이미 200 ms가 걸렸다면, 이전처럼
추가 100 ms를 기다리지 않습니다. 카메라·LiDAR·GPS도 동일한 주기 원칙을 따릅니다.

## 품질과 한계

카메라 `auto`는 처음부터 640×360 출력 범위와 JPEG Q70을 사용합니다. 종횡비를
유지하고 작은 원본을 확대하지 않으며, 사용자가 명시한 더 작은 출력 범위도 존중합니다.
회선이 느리면 먼저 FPS를 낮추고 자동으로 160×90 같은 화면으로 떨어뜨리지 않습니다.
좋은 연결에서는 960×540, 1280×720으로 올라갑니다. 첫 승급은 최소 3초 뒤, 다음
승급은 최소 5초 뒤에 가능하며 빠른 정상 디코딩 ACK가 10회 연속 필요합니다.
450 ms 초과 ACK가 3회 연속이거나 1초 초과이면 한 단계 낮추되 640×360 범위와
Q70 하한을 유지합니다. 명시적인 `tiny`·`slow` 선택은 비상 저용량 모드로 남습니다.

카메라 전용 상한은 최대 30 FPS·4 MB/s입니다. 이후 관측된 프레임 크기와 ACK 시간의
평활값으로 처리 속도를 추정하고 85%를 사용해 여유를 둡니다. ACK에는 왕복 지연과
브라우저 작업도 포함되므로 이 값은 물리적인 회선 대역폭 측정값이 아닙니다.
동시 시청자는 최대 4명이며 각자의 속도·출력 크기를 유지합니다. LiDAR·IMU·GPS가
사용하는 기존 `StreamBudget`은 바꾸지 않습니다.

브라우저는 정상 디코딩, 오류, 500 ms 디코딩 시간 초과를 별도 ACK로 보냅니다.
시간 초과 ACK를 정상 재생으로 간주하지 않으며, 실패하면 이전 영상을 유지합니다.
화면에는 마지막 정상 영상의 갱신 경과시간, 원본/수신 FPS, 회선 제한과 ACK 시간이
나옵니다. 이 경과시간은 카메라 촬영부터 표시까지의 절대 지연 측정값이 아닙니다.

로컬 시뮬레이션만 `DASHBOARD_MODE=simulation`과 `CAMERA_PREVIEW_LOCAL_FPS=30`을
함께 설정했을 때 카메라 전송 상한을 5 MB/s로 올립니다.
어두운 단색 화면뿐 아니라 복잡한 640×360 영상도 로컬에서 전송할 여유를 둡니다.
`slow`·`tiny` 프로필은 이 설정과 관계없이 기존 제한을 따릅니다. 이 설정은
Gazebo가 실제로 30 fps를 렌더링한다는 보장이 아닙니다.

ACK를 하나씩 확인하므로 왕복 지연만 200 ms인 연결도 전송·해독 시간을 제외한 이론상
상한이 5 FPS입니다. 복잡한 Q70 JPEG를 낮은 대역폭으로 보내면 갱신 간격이 수초가
될 수 있습니다. 같은 크기의 JPEG도 현재는 검증/재인코딩합니다. 원본 품질 메타데이터가
없어 무조건적인 원본 JPEG 통과 경로는 추가하지 않았습니다.

H.264/WebRTC 같은 프레임 간 압축은 후속 실측 후보입니다. 현재 JPEG 방식의 한계를
없앴다고 주장하지 않으며, Jetson Orin Nano의 하드웨어 인코더 사용 가능성을 가정하지
않습니다. 이번 변경은 코덱 설치·노출 변경·카메라 드라이버 변경을 포함하지 않습니다.

2026-09-30 실제 읽기 전용 확인에서 카메라 설정/협상 모드는 1920×1080·30 FPS·MJPG였고
10초간 실제 발행 빈도는 압축 약 15.00 Hz, 원본 BGR 약 3.95 Hz, 브리지 약 15.06 Hz였습니다.
라이브 압축 영상은 1280×720·Q70입니다. 자동 노출에 따른 프레임 속도 변화가 허용되어
있으며, 모드의 30 FPS 숫자가 실제 30 Hz 발행을 의미하지 않습니다. 캡처·노출은 유지합니다.

## 재현 가능한 검증

`tests/test_camera_policy.py`, `tests/test_camera_decode_ui.js`,
`tests/test_stream_budget.py`와 `tests/test_stream_latency.py`는 ROS·Jetson 없이
격리 컨테이너에서 실행합니다. 센서 네 종류의 ACK를 의도적으로 늦춰 두 번째
프레임이 누적되지 않고, ACK 후 최신 샘플이 오는지 확인합니다. 카메라 시청자
8개의 캐시 동시 요청은 JPEG 인코딩 1회를 공유합니다. 실제 웹소켓 시청자 수는 4명으로 제한합니다.
새 카메라 시험은 밝은 영상과 복잡한 JPEG, 최소 품질, 빠른 연결의 단계 상승,
디코딩 실패/시간 초과/오래된 연결 콜백, 원본 불변성과 실제 TCP 바이트 제한을 확인합니다.
로컬 TCP를 0.125 Mbps로 제한한 합성 시험에서도 83,548바이트 영상을 640×360·Q70으로
수신하고 ACK 후 최신 프레임을 선택했습니다. 이 결과는 실제 인터넷·과수원 영상·실차
30 FPS의 검증이 아닙니다. 아래 2026-09-28 수치는 변경 전 정책의 역사적 기록입니다.

2026-09-28 Windows Docker Desktop의 격리 loopback 측정:

| 항목 | 관측값 |
| --- | --- |
| 카메라 입력 | 합성 640×360 무작위 색 영상, 약 28.84 fps |
| binary JPEG 수신 | 약 28.84 fps, 3.80 MB/s |
| 늦은 IMU ACK 해제 후 최신 샘플 | 약 0.8–1.3 ms, 기존 추가 100 ms 대기 제거 |
| 전체 원본 대시보드 Python 테스트 | 120개 중 119개 통과, opt-in 통합 1개 제외 |

위 카메라 수치는 Gazebo·실제 USB 카메라·인터넷 링크의 측정값이 아닙니다.
테스트 스케줄러의 디버그 추적을 끄고 운영과 같은 asyncio 설정으로 측정했습니다.
실제 Jetson/브라우저 성능은 아래와 같이 별도로 확인했습니다.

`tests/test_ws_proxy_latency.py`는 실제 TCP 소켓으로 일반 HTTP 옵션 0, 인증된
WebSocket 양방향 옵션 1, 세션 없는 연결 거절, JPEG 디코딩 후 ACK 교환을 검사합니다.
추가 로컬 합성 실험에서는 원본 27.55 fps, 기존 옵션 프록시 24.89 fps,
`TCP_NODELAY` 프록시 27.36 fps였습니다. Jetson의 격리 합성 실험은 원본 28.89 fps,
기존 옵션 29.19 fps, 새 옵션 29.15 fps로 추가 이득이 없었습니다. 이 비교는 네트워크와
운영체제별 차이를 보여주며, 실제 카메라 프레임 개선을 보장하는 수치로 사용하지 않습니다.

## 실제 Jetson 적용 후 관찰

`4098bfd028b264261fcff86afa207373b6b7727b` 적용 후 실제 카메라 원본은
1280×720, 약 15 fps를 유지했습니다. 적용 전후 모두 3.00초 동안 45개 원본
프레임이 들어왔습니다. 원본 센서 속도를 30 fps로 변경한 것은 아닙니다.

원격 SSH 터널을 통한 실제 브라우저의 `Auto` 모드를 78.54초 동안 조작 없이
관찰했습니다. 151개 binary 프레임이 도착했고, 각 15초 구간은 약 1.93–2.00 fps,
160×90이었습니다. 표시 요청 상한과 예산은 끝까지 2 fps, 3 KB/s에 머물렀습니다.
LiDAR 표시도 60개 점으로 제한됐지만 원본 스캔에는 약 3,160개 점이 있었습니다.
같은 연결의 WebSocket ping 12회는 100.9–148.5 ms, 중앙값 128.49 ms였습니다.
기존 자동 품질 상승 조건인 연속 15회 120 ms 미만 ACK를 충족하기 어려웠습니다.

이 조건을 수정한 `3d63f167f5f6b88b7355726a2790d9380f409b71`을 배포하고,
같은 방식으로 새 브라우저 세션을 77.56초 관찰했습니다. 별도 품질 선택 없이
284개 binary 프레임을 받았으며 마지막 디코딩 영상은 640×360이었습니다.

| 15초 관찰 구간 종료 | 수신 fps | 마지막 영상 | 마지막 유효 프로필 | 마지막 ACK |
| --- | --- | --- | --- | --- |
| 16.54초 | 1.93 | 160×90 | tiny | 174 ms |
| 31.56초 | 3.93 | 320×180 | slow | 136 ms |
| 46.57초 | 2.47 | 160×90 | tiny | 151 ms |
| 61.60초 | 3.73 | 320×180 | slow | 118 ms |
| 76.64초 | 6.53 | 640×360 | balanced | 115 ms |

연결 상태에 따라 중간에 품질이 낮아졌지만, 이전처럼 2 fps에 고정되지 않고
회복했습니다. 마지막 LiDAR 표시는 180개 점이었고 원본은 약 3,130–3,160개였습니다.
실제 원본 카메라는 후속 수정 뒤에도 1280×720, 약 15 fps를 유지했으며 3.001초 동안
46개 프레임을 받았습니다. 원본 센서 속도와 표시 전송 속도는 구분해야 합니다.

두 관찰 동안 카메라·LiDAR·IMU는 연결 상태를 유지했고 새 안내 문구를 확인했습니다.
JavaScript 오류와 쓰기 요청은 모두 0개였습니다. GPS는 아직 실제 수신기가 연결되지
않아 위치 고정이 없으며, 브리지의 상태 갱신만 확인했습니다. 별도 프로필 선택이나
원본 카메라 설정 변경으로 수치를 높이는 작업은 하지 않았습니다.

후속 `TCP_NODELAY` 수정 `6e2a5ad56d67347adfc94f1aa1059ffc303f7bd7`도 같은
6개 앱 서비스에 적용했습니다. 실제 센서 브리지 네 종류의 WebSocket 연결을 열어
업그레이드 성공과 소켓 옵션 1을 확인했습니다. 새 Auto 브라우저 관찰 78.86초 동안
287개 프레임을 받았으며, 마지막 15초 구간은 640×360, 5.60 fps, 마지막 ACK 163 ms였습니다.
LiDAR 표시는 450개 점, 실제 카메라 원본은 약 15 fps였고 오류·쓰기 요청은 0개였습니다.
이전 관찰의 마지막 6.53 fps/115 ms ACK와 네트워크 상태가 달라, 이 수치로 실차의 추가
FPS 개선을 주장하지 않습니다. 변경 목적은 소켓이 불필요하게 작은 패킷을 기다리는
조건을 제거하는 것입니다.

대시보드를 재시작하면 기존 WebSocket 세션은 끊깁니다. 다음 HTTP telemetry 요청이
새 세션 쿠키를 발급하고 각 센서가 재연결합니다. 녹화·조종 세션을 자동 재개하지는 않습니다.
