# 실시간 우선 매핑과 작업 관리

실시간 지도는 서버의 단일 raw LiDAR·native IMU·품질 GNSS mapper를 사용한다.
여러 기기에서 화면을 열어도 계산 worker가 늘어나지 않는다. 기록 계산은 최대
하나이고 실시간 매핑이 시작되면 스캔 경계에서 대기한다. 이미 계산한 기록의
격자 셀 조회는 계속 가능하다. 이 기능이 실차 자율주행 출력 권한을 부여하지는 않는다.

대시보드의 실시간 지도 아래 **매핑 작업 관리**를 열면 실행 단계, 원시 입력 수,
지도에 누적한 스캔 수, 큐·손실, 최근 진척, 기록의 요청·처리 시각과 원인을 볼 수 있다.
대시보드 및 mapper 자식 프로세스 CPU는 1코어를 100%로 표시한다. 메모리는
대시보드 프로세스 RSS다. 카메라·ROS·기록 드라이버의 사용량은 이 수치에 포함하지 않는다.

**이 작업 중단**은 원본과 완료한 지도를 보존한다. 실시간 중단은 전용 raw
구독과 위치 정합도 멈춘다. 기록 중단은 worker를 종료하며 이전 요청의 제어 세대를
폐기한다. 화면이 갱신된 뒤 명시적으로 재생해야 이어간다. 초기화·중단의 epoch
검사는 다른 기기가 이미 바꾼 지도에 오래된 작업을 적용하지 못하게 한다.

기록 제어권은 한 기기가 갖는다. 다른 기기는 지도 조회는 가능하지만 해당 기록의
재생 시각·일시정지·초기화를 덮어쓸 수 없다. 마지막 제어 요청 후 15초가 지나면
고아 worker를 종료한다. 새 지도 만들기는 이전 worker가 끝난 뒤 새 history를
설치하며, 녹화 종료만으로 전체 기록을 계산하는 숨은 작업은 시작하지 않는다.

HTTP는 완료된 숫자 셀 묶음을 읽으며, 위치 정합의 긴 계산을 기다리지 않는다.
기록 지도·셀 창 조회는 동시 2개로 제한한다. 용량 초과 시 명시적 충돌 응답을
보내며 대시보드는 마지막 지도를 유지하고 재시도한다. live 큐는 8개,
IMU 대기 이력은 100개로 제한하고 손실을 표시한다.

누적 36,000개 스캔 뒤 강제 중단하던 제한을 제거했다. 진단용 pose/GNSS 이력만
제한하며 기존 격자는 유지한다. 센서 지연·정합 실패·worker 오류를 드러내지만,
불확실한 이동을 임의로 만들어 격자를 그리지는 않는다. 재시작 뒤 저장 지도는
차량의 현재 위치를 증명하지 않으므로 새 위치 추정이 필요하다.

Jetson에 `c8d3516` 구현과 `a8859e0` 화면 제어 ID 수정을 직접 SSH로 적용했다.
ARM 64개 검사와 웹 22종 검사를 통과했다. 다른 12개 역할·보호 원본 파일 59개·
설정과 기존 저장 지도는 배포 시 보존했다. GitHub Actions를 사용하지 않았다.

실제 화면에서 새 지도를 생성하고 470개 스캔을 누적한 뒤 작업 관리로 중단했다.
중단 후 12초 동안 스캔 수가 유지됐고 전용 LiDAR·IMU·GPS 연결도 유휴 상태였다.
관찰한 처리 지연은 약 42–49ms, 대기 큐는 0이었다. 정지된 차량 검사이므로
이 수치로 주행 중 기하 정확도를 주장하지 않는다. GPS는 유효 fix가 있을 때만 쓴다.

실제 기록의 이미 생성한 약 307초 구간에서 두 기기 제어 충돌과 오래된 명시적
재개 요청 차단을 확인했고, 기존 기록 지도 이력 해시가 유지됐다. 화면 내부의
view epoch와 서버 제어용 epoch를 분리해 정상 새 지도 요청이 거부되던 문제도 고쳤다.

유휴 자원의 주된 항목은 계속 동작하는 카메라 드라이버였다. mapper 전용 구독은
중단 시 닫지만 표시·원본 녹화용 센서 서비스는 유지한다. 장거리 기하 정확도,
기울기·빔 시각 검증과 실차 자율주행은 별도 미완료 항목이다.
