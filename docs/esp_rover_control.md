# ESP 로버 제어 (ESP32-S3 조종 브리지, 옛 ESP8266 V2)

2026-11-16 차의 보드가 바뀌었다. 옛 ESP8266(차동 V2 펌웨어)을 빼고 ESP32-S3 하나에 BTS7960 모터 드라이버 3개를 달았다.
1절이 지금 보드, 2절부터는 옛 ESP8266(차동 V2)의 기록이다(코드는 그대로 남아 `ROVER_ESP_KIND=esp8266_v2`, 기본값).

## 1. ESP32-S3 + BTS7960 3개 (2026-11-16 ~)

| 항목 | 값 |
| --- | --- |
| 보드 | ESP32-S3, 네이티브 USB(USB Serial/JTAG, 303a:1001). Jetson `/dev/serial/by-id/usb-Espressif_USB_JTAG_serial_debug_unit_30:30:F9:3C:D8:60-if00` → `/dev/ttyACM1`(2026-11-16) |
| 드라이버 | BTS7960 3개: 1 = 조향(일반 DC 모터, 가변저항 GPIO6), 2 = 왼쪽 구동, 3 = 오른쪽 구동 |
| 펌웨어 | `ABS-HOLD-8-REBOUND-LIMITS`(소스 `BTS7960_Serial_Control.ino`, 개발자 제공). 115200, 줄 단위 글자 명령 |
| 조향 명령 | `ANGLE -20..+20`(명령 눈금 도, **+ = 오른쪽**), 보정 RIGHT=1681 CENTER=1900 LEFT=2180(가변저항 값). ±20 은 명령 눈금이고 실제 바퀴 각도는 재지 않았다 |
| 구동 명령 | `2 F 100`, `3 R 80`(0~255), `2 S`, `STOP`(세 모터 모두) |
| 상태 | `STATUS` → `FW: ...`, `CAL: ...`, `STATUS: POT=... COMMAND_EQUIV=±d.dd HOLD=ON/OFF TARGET_POT=... TARGET_COMMAND=...` |

펌웨어에서 호스트가 꼭 알아야 하는 것(소스에서 읽음, 차에서 재지 않음):

- **원본 펌웨어는 구동 모터 2·3 에 시간 제한이 없었다.** `2 F 100` 은 STOP, `2 S`, 새 명령, 리셋 전까지 돈다. 2026-11-16 사용자 승인으로 펌웨어 구동 감시 패치를 보드에 썼다(모터 전원을 끈 채, 16 MB 전체 플래시 백업 뒤, app0 만 씀). 지금 보드는 FW 줄에 `DRIVE_WD=300`을 내고, 구동 명령이나 `HB`가 300 ms 없으면 모터 2·3 을 멈추고 `DRIVE STOP: WATCHDOG 300ms`를 낸다(감시 패치와 빌드·백업 기록은 조정 쪽 기록 폴더 `runs/fw_watchdog_20261116/`, 원본으로 되돌리기는 백업으로).
  브리지는 FW 줄의 `DRIVE_WD`를 보면 구동 중 0.1 s 마다 `HB`를 보내고, 감시 정지 줄이 오면 조종권을 거두고(`mcu_drive_watchdog`) 다시 돌리지 않는다.
- 조향 수동 명령(`1 F n`)은 1000 ms 뒤 선다. `ANGLE` 유지는 STOP·수동 조향·결함 전까지 이어지고, 한 목표에 보정 구동 1000 ms 한도가 있다.
  새 목표는 300 ms 조용히 기다린 뒤 50~80 ms 펄스를 준다. 그래서 목표를 0.4 s 보다 자주 바꾸면 바퀴가 움직이지 않는다.
- USB 포트를 열면 보드가 다시 켜졌다(2026-11-16 한 번 관측). 다시 켜지면 모든 출력이 꺼지고 설정 배너(FW, CAL, STATUS, READY, 안내 세 줄)가 나온다.

### 1-1. 브리지 (`ROVER_ESP_KIND=esp32_abs_hold`)

`python3 -m scripts.esp_rover_bridge`(ROVER_ESP_KIND 로 고름) 또는 `python3 -m scripts.esp32_steer_bridge`. 파일: `scripts/esp32_abs_hold.py`(줄 해석, 명령,
단위, USB 전송, 모터 어댑터와 안전 층), `scripts/esp32_steer_bridge.py`(제어 소켓, 요청 큐, ROS, 상태 파일).

- 한 프로세스만 포트를 연다: by-id 경로, 열 때마다 udev `ID_SERIAL` 확인, 장치 번호별 flock, TIOCEXCL. 제어 소켓 옆 `bridge.lock` 이 두 번째 브리지를 막는다.
- 조종 규칙은 조향 차량과 같다(`scripts/steer_control_core.py`, 바꾸지 않음): arm 에 `vehicle_profile: front_steer`, lease·일회용 ticket·seq,
  deadman, 입력 기한 0.75 s, ticket 1.5 s, 유휴 30 s, 자동 재무장 없음. 대시보드 조향 패널과 실행기의 요청 형식(`throttle`, `steer_mrad`) 그대로다.
- 부호: 조향 API 의 `steer_mrad` 는 **왼쪽 +**, 펌웨어 `ANGLE` 은 **오른쪽 +** 다. 브리지는 `ANGLE = -(steer_mrad 를 도로 바꾼 값)` 을 보낸다
  (시험 `tests/test_esp32_bridge.py`: 왼쪽 +349 mrad → `ANGLE -20.0`, 측정 `COMMAND_EQUIV` −도 → `measured_mrad` +). 소프트 한계 349 mrad(20 명령 도).
- 조향 목표(펄스 유지 펌웨어. SMOOTH 판은 1-5절): 1 명령 도 단위, `ANGLE` 사이 0.5 s 이상(가장 새 목표가 이김), 한 목표는 측정각에서 20 도 이내(왼쪽 끝 → 오른쪽 끝은 두 번에.
  한 번에 보내면 펌웨어의 1000 ms 보정 한도가 중간에 끝난다: 가짜 펌웨어 시험), 펌웨어가 취소한 목표는 요청이 바뀔 때까지 다시 보내지 않는다(강제 재시도 없음).
  arm 직후 첫 목표가 지금 각도와 같으면(0.5 도 안) 보내지 않는다.
- 구동: `throttle` → `2 F/R pwm` + `3 F/R pwm`, pwm = (|t| × 255 + 50) // 100, 호스트 상한(`ROVER_ESP32_MAX_DRIVE_PWM`). 앞으로 가는 방향은
  `ROVER_ESP32_LEFT_FORWARD`, `ROVER_ESP32_RIGHT_FORWARD`(기본 F, **현장 미확인**).
- 한 줄 깨짐(2026-11-17 08:47 차에서: USB 로 오는 바이트가 빠져 FW 줄이 `FW: MITS F=RIGHT …` 로 읽혔고, 브리지가 `firmware_mismatch` 에
  묶여 재시작 전까지 조종 활성화를 거절함): 다른 펌웨어 이름은 FW 줄 3개가 잇달아 같을 때만 믿는다(`FW_MISMATCH_LINES`, 그 뒤는 전처럼 래치).
  그보다 적으면 `counts.fw_line_mismatch` 로 세고 사건 `fw_line_corrupt`(10 s 에 한 번)만 남긴다. 이름이 맞는 FW 줄의 토큰(DRIVE_WD, CAL_RUNTIME,
  SMOOTH)이 바뀌거나, 보정 작업이 없는데 CAL 값이 바뀌면 다음 줄이 같을 때 받는다. 끝까지 맞지 않는 CAL 줄은 `cal_line_corrupt` 로 세고 버린다.
  STATUS 줄 하나가 깨져도 아무 래치도 걸리지 않는다(시험 `tests/test_esp32_corrupt_lines.py`).
- 상태: 10 Hz `STATUS`. 상태 응답에 `steering`(측정 mrad, 명령 도, 가변저항 값, 유지 목표, `age_ms`, `age_limit_ms` 300, 결함),
  `steer_control`(`keys: full_limit` → 화면이 A/D 를 끝까지, 끌기 막대), `drive`(원하는 값, 펌웨어가 확인한 값, TTL), `outputs`(V2 핀 이름 관례 D8/D5/D3/D0 에 확인된 구동 duty).

### 1-2. 구동 안전 (호스트 쪽 겹, 펌웨어 감시 300 ms 와 함께)

| 경우 | 브리지가 하는 것 |
| --- | --- |
| 입력 기한(0.75 s) 만료, 조종권 잃음(ticket·seq 오류, 다른 화면), 해제, 화면 STOP·Esc | `STOP`(세 모터) |
| 구동 TTL(0.75 s, 조종 규칙과 따로) 만료 | `2 S`, `3 S` 즉시 |
| STOP·`2 S`·`3 S` 의 `OK:` 답이 없음 | 0.15 s 마다 다시. 0.6 s 넘게 없으면 `stop_unconfirmed` 래치, STOP 한 번 더, 포트를 닫고 2 s 뒤 다시 엶 |
| 정지 중 | 1 s 마다 `2 S`, `3 S` 다시(0 유지) |
| 구동 값 | 바뀔 때만 쓴다. 같은 값을 다시 쓰지 않는다(스스로 리셋된 보드를 호스트가 다시 돌리지 않게) |
| 보드 리셋(READY 줄) | `mcu_reset_detected` 래치, 조종권 해제, STOP. 다시 조종하려면 사람이 활성화 |
| 펌웨어 감시(`DRIVE_WD=300`, 2026-11-16 보드에 씀) | 구동 중 0.1 s 마다 `HB`. `DRIVE STOP: WATCHDOG` 줄이 오면 조종권 해제(`mcu_drive_watchdog`), 다시 돌리지 않음 |
| STATUS 0.6 s 없음, 가변저항 무효가 0.6 s 넘게 이어짐(순간 무효는 유예, 2026-11-18) | 조종권 해제, STOP |
| 직렬 오류(쓰기·읽기 실패, 끊김) | `hardware_fault` 래치, 조종권 해제, STOP 시도, 포트 닫고 2 s 뒤 다시 엶(열면 보드가 다시 켜질 수 있다) |
| 포트를 연 직후 | STOP 먼저(이전 프로세스가 남긴 구동이 있을 수 있음), READY 또는 3 s 뒤 STOP·STATUS 답 확인 |
| SIGTERM·SIGINT·SIGHUP, atexit | STOP 뒤 포트 닫음(시험: pty 끝단 SIGTERM → 보드 구동 0) |

**남는 위험.** 브리지 프로세스가 SIGKILL·멈춤·Jetson 전원 문제로 죽었는데 보드가 USB 로 계속 전원을 받으면 마지막 구동 명령이 계속 돈다
(pty 끝단 시험에서 SIGKILL 뒤 1 s 넘게 구동 그대로임을 확인). 포트가 닫힐 때 보드가 리셋되는지는 재지 않았다. 대시보드 STOP 은 물리 전원 차단이 아니다.
이 틈은 펌웨어의 구동 감시(마지막 구동 명령이나 `HB` 줄 뒤 300 ms 면 2·3 정지)로만 닫힌다. 그 펌웨어가 FW 줄에 `DRIVE_WD=300` 을 내면 브리지는 구동 중
0.1 s 마다 `HB` 를 보낸다(2026-11-16 보드에 씀, FW 줄 `DRIVE_WD=300`).

### 1-4. 실시간 조향 보정 (펌웨어 `CAL_RUNTIME=1` 필요, 2026-11-16 제안)

좌우 끝(가변저항 값)은 배터리 전압, 바닥, 하중에 따라 날마다 다를 수 있다. 그래서 보정 표시(RIGHT/CENTER/LEFT)를 펌웨어에 고정하지 않고
보드의 NVS(Preferences 이름공간 `steer_cal`)에 두고, 대시보드에서 다시 잴 수 있게 했다. 사용자 요청: 왼쪽 최대 20°, 오른쪽 최대 20°.
명령 ±20 은 지금처럼 명령 눈금이다. 보정 뒤 ±20 은 "찾은 끝에서 여유만큼 안쪽"이 되고, 실제 바퀴 각도(°)는 여전히 재지 않았다.

**하는 일.**

| 단계 | 화면(Rover Control → 주행 제어 → 조향 보정, 접힌 칸) | 펌웨어 |
| --- | --- | --- |
| 가운데 | `지금 위치를 가운데로`: 바퀴를 똑바로 둔 뒤 누른다 | `CAL CENTER`(650 ms 조용히 잰 중앙값) + `CAL SAVE` |
| 왼쪽 끝 | `왼쪽 끝 찾기` | `CAL FIND LEFT`: 조향 모터만, PWM 100 으로 100 ms 밀고 650 ms 끈 뒤 정착 값을 잰다. 되밀림 20 count 이상, 남은 진척 3 count 이하, 하드 한계, 펄스 40개·구동 4 s·전체 40 s 중 먼저 오는 것에서 멈추고 `CAL FOUND LEFT POT=… REASON=…` |
| 오른쪽 끝 | `오른쪽 끝 찾기` | `CAL FIND RIGHT`(같은 방법) |
| 적용 | `적용`(왼쪽·오른쪽 여유, 기본 30 count, 10~120) | `CAL SET LEFT 찾은값-여유`, `CAL SET RIGHT 찾은값+여유`, `CAL SAVE`. 브리지가 CAL 줄을 다시 읽어 대조 |
| 기본값 | `기본값으로` | `CAL DEFAULT`(1681 / 1900 / 2180, NVS 지움) |

끝 찾기는 개발자 기록(`REBOUND_CALIBRATION.md`, `rebound_measure.py`)의 방법과 멈춤 규칙 그대로다. 찾은 값은 스스로 보정을 바꾸지 않고, `적용`을 눌러야 쓰인다.
쓸 수 있는 끝은 멈춘 까닭이 되밀림·진척 없음이고 시작점에서 20 count 이상 바깥인 것뿐이다(STOP·입력으로 중단, 하드 한계, 무효, 예산 끝은 쓰지 않음).
가운데 근처에서 시작하면 빠르다(가짜 보드 자리값: 가운데 → 끝 약 10 s, 반대쪽 끝에서 건너가면 약 18 s).

**안전.**

- 펌웨어는 모든 CAL 명령(값 출력 `CAL` 만 빼고)을 모든 모터가 서 있을 때만 받는다: 조향 유지·시험 없음, 모터 2·3 이 꺼진 지 1 s 이상. 아니면 `CAL ERROR: … REFUSED: …`.
- 하드 한계: RIGHT ≥ 1300, LEFT ≤ 2500, CENTER 1800~2000, 가운데에서 양쪽 150 count 이상. 모든 SET·부팅 때 읽은 NVS 값에 검사한다(밖이면 기본값).
  SMOOTH 판은 LEFT ≤ 2600, r2 는 CENTER 1850~2150 이다(1-5절). 브리지는 좌우 한계를 CAL 줄의 `GUARD=` 에서 읽는다.
  가변저항 무효 창은 보정 표시가 아니라 하드 한계 ±100(1200~2600)을 따른다(넓은 보정을 쓸 수 있게).
- 끝 찾기는 조향 모터만 쓴다. PWM 은 100 을 넘지 않고(위치 제어와 같음) 펄스는 100 ms 를 넘지 않는다. **아무 직렬 입력**(STOP 포함)이 오면 곧 멈춘다.
- 브리지(`op calibrate`)는 조종 활성화가 꺼져 있고(lease 없음) 움직이지 않을 때만 받는다(`calibration_needs_disarmed` / `calibration_needs_standstill`).
  늘 STOP 을 먼저 보내고 확인받은 뒤 CAL 줄만 보낸다. 작업 동안 STATUS, 0 유지(`2 S`/`3 S`), `HB`, `ANGLE` 을 멈춘다(STATUS 한 줄도 스캔을 멈추게 하므로).
  모터 2·3 명령은 보내지 않는다. 작업 중에는 조종 활성화가 `calibrating` 으로 거절된다.
- 화면·상태 막대의 STOP, Esc, 이 칸의 STOP 은 작업을 끝낸다(브리지가 STOP 을 보내면 펌웨어 스캔이 멈춘다). 스캔 중 화면을 숨기거나 떠나면 STOP 을 보낸다.
  보드가 3 s 넘게 아무 줄도 안 내면 브리지가 STOP 을 보내고 작업을 끝낸다(`calibration_silent`). 자율 run 중에는 대시보드가 거절한다(넘겨받지 않음).
- 펌웨어 쪽 구동 감시(300 ms), 모터 2·3 동작, 유지 규칙(1 s 보정 예산, 되밀림·무진척 취소)은 그대로다.
- **나눠 가는 목표.** 보정이 넓어지면(예: 한쪽 400 count) 가운데 → ±20 한 목표가 펌웨어의 1000 ms 보정 예산을 넘어 중간에 취소된다(펌웨어 PC 시험).
  그래서 브리지는 한 `ANGLE` 목표를 280 count 이하로 나눈다(`STAGE_MAX_COUNTS`, 자리값). 기본 표시(넓은 쪽 280 count)에서는 지금처럼 20° 한 번이다.

**펌웨어 업데이트가 한 번 필요하다.** 지금 보드의 펌웨어(`ABS-HOLD-8-REBOUND-LIMITS … DRIVE_WD=300`)에는 이 명령이 없다. 브리지는 FW 줄의
`CAL_RUNTIME=1` 을 보고 판단하고, 없으면 아무것도 보내지 않고 `calibration_needs_firmware_update` 로 답한다(화면 버튼도 그 까닭으로 꺼짐).
새 펌웨어는 펌웨어 이름 `ABS-HOLD-8-REBOUND-LIMITS` 를 그대로 두므로 지금 브리지도 그대로 붙는다(새 줄은 모르는 줄로 셀 뿐). 처음 쓰면 NVS 가 비어 있어 지금과 같은 기본값으로 돈다.
소스·빌드·PC 시험은 조정 쪽 기록 폴더 `runs/steer_runtime_cal_20261116/fw/`(README_KO.md).

**쓰기는 차를 받침에 올리거나 구동 모터 선을 뺀 채로 한다.** esptool 로 쓰는 약 10 초 동안 보드는 리셋·다운로드 모드라 펌웨어가 돌지 않고,
모터 드라이버 핀(EN·PWM)을 소프트웨어가 잡지 못한다(STOP 도, 구동 감시도 없다). 앞바퀴가 땅에 닿은 채 사람이 개입할 수 없으면 "확실히 구동 안 함"을 보장할 수 없다.
그래서 원격으로 쓰지 않는다. 순서는 이 레포의 `deploy/jetson_esp32_bridge/README_KO.md` 8절.

### 1-5. SMOOTH 펌웨어 (FW 줄 `SMOOTH=1`, 2026-11-16 저녁)

조정 쪽 기록 `runs/steer_smooth_20261116/fw/`(make_smooth.py + r2_changes.py)의 판이다. 펌웨어 이름은 그대로라 브리지가 그대로 붙고,
FW 줄 끝의 `SMOOTH=1`(`SM OFF` 면 `SMOOTH=0`)을 보고 규칙을 고른다.

- **펌웨어.** (2026-11-19 보드 값: PWM_MIN 70, PWM_MAX 160(펌웨어 최대), RESTART_TOL 10, STOP_TOL 6, STALL_MS 200, BOOST 15,
  `SM` 명령으로 NVS 에 씀. 아래 숫자는 처음 판의 기본값이다.)
  `ANGLE` 유지가 조향 모터를 끊지 않고 돌린다: PWM 이 PWM_MIN 60 에서 PWM_MAX 100 으로 오르고, 목표 SLOW 120 count 안에서 줄고,
  STOP_TOL 6 count 안에서 끈다(r2 는 끝에 BRAKE_MS 40 ms 제동). 목표마다 1000 ms 예산과 새 목표 앞 300 ms 기다림이 없고, 달리는 방향 앞쪽의 새 목표는
  멈추지 않고 이어받는다. 스스로 멈추는 경우: 진척 없음(STALL), 한 번 5 s(RUN TIME LIMIT), 4번 안에 못 닿음(NO CONVERGENCE). 모두 강제 재시도 없음.
- **브리지(`SMOOTH=1` 일 때만).** `ANGLE` 은 0.1 s 간격(가장 새 목표가 이김, 2026-11-18 에 0.2 s 에서 줄임), 0.25 명령 도 단위(소수 둘째 자리, 예 `ANGLE -12.25`), 나누지 않는다
  (한 목표가 끝에서 끝까지). 옛 0.5 s 간격과 280 count 나누기가 움직임을 끊기게 했다. 토큰이 없거나 `SMOOTH=0` 이면 옛 규칙(1 도, 0.5 s, 280 count) 그대로다.
- **화면 A/D.** 지금처럼 끝 목표 하나다. 펌웨어가 한 번에 이어서 가므로 끊기지 않는다. 화면이 목표를 조금씩 올리면 바퀴가 목표에 닿아 섰다가 다시
  가므로(펌웨어 규칙) 그렇게 하지 않았다. 놓으면 가운데로, ‘각 유지’면 그대로.
- **끌기 막대.** 0.25° 단위, 0.05 s 마다 새 목표(브리지가 0.1 s 로 묶음), 값은 소수 한 자리로 보인다. 빠르게 끌면 앞쪽 목표를 이어받아 한 번에 가고,
  아주 느리게 끌면 목표가 몇 count 씩만 움직여 펌웨어가 닿고 섰다 다시 간다(가짜 보드에서 본 성질).
- **W/S.** 화면은 조종권, 상태 신선함, 속도 상한 말고는 막지 않는다. 브리지의 구동 상한(설치 값 `--max-drive-pwm`, 상태 `drive.max_pwm`)을 '구동 duty'
  칸 아래에 보이고, 0 이면 W/S 를 누를 때 "구동 상한 0" 이라고 말한다. 구동 기본값과 안전 한계는 바꾸지 않았다.
- **상태.** `steer_control.smooth`, `angle_min_interval_ms` 200, `angle_quantum_deg` 0.25, `angle_max_jump_deg` 40, `stage_max_counts` null.
  `steering.smooth`: FW 토큰, SM 줄(MODE, 값, STORE), 마지막 SM 답, DATA 줄 수. 부팅 줄에 SM 줄이 없었으면 연결마다 한 번 `SM`(읽기만)을 보낸다.
  브리지는 `SM SET/ON/OFF/SAVE/DEFAULT` 나 `TRACE` 를 보내지 않는다. TRACE 의 `DATA,...` 줄은 따로 센다(모르는 줄로 세지 않음).
- **보정.** 좌우 하드 한계는 CAL 줄의 `GUARD=1300..2600` 을 읽는다(없으면 1300/2600). 가운데 범위는 CAL 줄에 없어서 r2 의 1850~2150 을 쓴다.

  `pulse_ms`(40~100 ms, 예 `CAL FIND LEFT 60`)를 줄 수 있다(SMOOTH 판만, 옛 판이면 `calibration_pulse_needs_firmware_update`). 화면 버튼은 기본 100 ms 그대로다.

  6.6 s(목표 3개), 13.4 s(목표 5개). 시험 `tests/test_esp32_smooth.py`, `tests/test_steer_drag.mjs`.

### 1-6. 거리 이동 (지형별 duty 표, 2026-11-17)

Rover Control → 수동 조종 탭 → 주행 제어 → '거리 이동'(접힌 칸). 방향(앞으로·뒤로), 지형, 거리(앞으로 0.2~3.0 m, 뒤로 0.2~2.0 m, 기본 1.0 m)와 속도(duty)를 고르고
버튼을 **누르고 있는 동안만** 간다. 줄자로 잰 거리는 보정·설정 탭의 '거리 이동 줄자 보정'에 넣는다. 메뉴는 그대로 8개다.
2026-11-20: 줄자 보정에도 지형 고르기가 있다. 거리 이동의 지형과 같은 값이라 한쪽을 바꾸면 다른 쪽도 바뀐다. '줄자 보정 지우기'는 고른 지형에 간다.
줄자 거리는 그 이동을 계획한 지형에 쌓이므로, 고른 지형이 마지막 이동의 지형과 다르면 저장 버튼이 꺼지고 그 까닭을 보인다.

- **뒤로 (2026-11-19, 사용자 요청 "특정거리 앞으로 가는거 뿐만 아니라 뒤로 가는 기능").** `plan`·`start` 의 `direction: "backward"`(없으면 앞으로).
  서버가 같은 duty 를 음의 throttle 로 보낸다(브리지 `drive` 는 -100..100, 구동 상한은 |throttle| 에 그대로). 앞으로의 규칙(조종 활성화, 누르고 있기,
  STOP, 구동 1.3~10 s, 브리지 상한)이 모두 같고, 뒤를 보는 센서가 없어서 거리는 **2.0 m 까지**다(넘으면 `distance_out_of_range_backward`).
  속도 표는 앞으로만 잰 것이라 뒤로 계획의 등급은 '가정'이다. 줄자 보정은 방향마다 따로 쌓는다: 뒤로 계획은 앞으로 표본을 빌려 쓰지 않는다(뒤로 표본이 없으면 1.00).
  표본에 `direction: "backward"` 가 붙고, 방향이 없는 옛 표본은 앞으로다. `GET /api/rover/distance` 의 보정은 지형마다 `duties`(앞으로)와 `backward_duties`.
  `reset` 에 `direction` 을 주면 그 방향만 지운다(없으면 지형 전체, 전과 같음). 잘못된 방향은 `distance_direction_invalid`.
- **속도 밀대와 브리지 상한.** 밀대의 위 끝은 그 지형 표의 가장 높은 duty 와 계획 답 `bridge.max_duty`(브리지 구동 상한 안의 가장 큰 duty) 가운데 작은 쪽이다.
  2026-11-19 구동 상한을 100 %(PWM 255)로 올린 뒤에는 표 전체가 고를 수 있다. 상한이 바뀌면 다음 계획 답에서 밀대가 따라간다.

- **자료.** `config/drive_terrain_table_202610.json`. 시뮬레이션 레포 `docs/drive_response/`(2026-11-12 분석)의 표 T3(지면별 duty→속도),
  T4s(출발), T5s(정지), T6(정지에서 출발한 이동거리)를 값마다 출처·등급·구간 수와 함께 옮겼다. **2026-10-03·10-10, 조향 장치를 달기 전 차(ESP8266,
  좌우 차동, 펌웨어 구동 램프 100 %/s)의 수동 주행 기록이다. 지금 차(ESP32-S3, BTS7960, 펌웨어 구동 램프 없음·3dba62c 부터 브리지 램프, 조향 장치 무게)는 재지 않았다.**
  지형: 도로·포장(10/3), 과수원 열 안(10/10), 과수원 그 밖(10/10), 과수원 10/3(열 구분 없음). 등급: 측정 = 구간 5개 이상, 참고 = 1~4개,
  모델 = 분석의 식, 가정 = 다른 경우에 잰 값을 빌려 씀.
- **속도 고르기 (2026-11-19, 사용자 요청 "거리 이동하는거 속도 조절 되게").** 화면의 '속도 (duty %)' 밀대: 그 지형 표의 가장 낮은 duty 부터 가장 높은
  duty 까지 1 % 단위(도로·포장 40~100 %, 과수원 열 안·그 밖 90~100 %, 과수원 10/3 45~100 %). 밀대 옆에 duty, 그 duty 의 표 속도(m/s), 계획 시간이
  보인다. 표에 있는 duty 는 그 행의 값을, 두 행 사이 duty 는 두 값의 직선 보간을 쓴다(등급 '모델', 화면에 "표의 40 %·58 % 사이 직선 보간"처럼 보임).
  표 밖(외삽)은 내지 않는다. 처음 값은 그 지형 표의 가장 낮은 duty(11-17 화면의 첫 선택과 같음)라서, 그때 잰 줄자 보정이 그대로 쓰인다.
  표에 있는 duty 의 계획은 3dba62c 와 같다(시험이 값을 고정).
  요청: `POST /api/rover/distance/plan`·`start` 의 `duty`(정수 %, 없으면 그 지형의 기본 duty). 정수가 아니면 `distance_duty_invalid`, 표 범위 밖이면
  `distance_duty_out_of_range`, PWM 이 브리지 구동 상한보다 크면 `distance_duty_above_cap`(계획 답의 `bridge.max_duty` 가 상한 안의 가장 큰 duty).
  계획 답에 `duty_min`·`duty_max`·`default_duty`, `speed.interpolated`·`speed.between`, `correction`(factor, samples, from_duty, exact)이 있다.
- **계획 식** (`dashboard_server/drive_distance.py`). 속도 v(T3), 출발 지연 L = 2 s − s100(2 s)/v100 = 2 − 1.29/0.928 = 0.61 s
  (100 % 정지 출발 9건, 다른 duty 는 '가정'), 놓은 뒤 미끄러짐 C = 0.55 m(100 % 측정 7건) 또는 모델 v·0.25 + v²/2.6, 지형·속도 보정 배율 c.
  T 초 구동하면 예상 거리 E(T) = c·(v·(T − L) + C). 거꾸로 T = L + (D/c − C)/v. T 가 1.3 s(정상 속도 90 %까지 p50 1.28 s, T4s)보다 짧으면
  "이 속도로는 너무 짧다"로 거절한다(예: 도로 100 % 는 1.2 m 부터, 40 % 는 0.4 m 부터). 화면에 계획 시간, 예상 거리, 각 부분의 값과 등급이 보인다.
- **보정.** 이동이 계획 시간까지 끝나면 줄자로 잰 실제 거리를 넣는다. 표본 = 실제 / 모델(실제 구동 시간). 2026-11-19 부터 **지형과 속도(duty)마다**
  그 duty 에서 잰 최근 5개의 중앙값을 0.5~1.5 로 묶어 다음 계획에 쓴다. 고른 duty 에 기록이 없으면 그 지형에서 가장 가까운 기록 있는 duty 의 배율을
  빌려 쓰고(같은 거리면 표본이 많은 쪽, 그다음 낮은 쪽), 화면 '보정 배율' 줄에 "40 %에서 잰 배율을 빌려 씀"처럼 어느 속도의 값인지 보인다.
  '줄자 기록 있는 속도' 줄에 duty 별 배율과 표본 수가 보인다. duty 마다 최근 20개를 남긴다. 파일 `runtime/drive_distance_corrections.json`
  (환경 변수 `UBTS_DRIVE_DISTANCE_FILE`, 형식은 11-17 그대로: 표본마다 duty 가 이미 들어 있어 옮길 것 없음). 지형별 '줄자 보정 지우기' 버튼(그 지형의 모든 속도).
- **구동 경로와 안전.** 이 화면이 조종 활성화를 쥐고 있어야 한다. 누르면 화면이 조종권(lease·ticket·seq)을 서버에 넘기고, 서버가 브리지의 보통
  `drive` 요청(owner, 일회용 ticket, seq+1, deadman, 입력 기한 0.75 s)을 0.1 s 마다 보내다가 계획 시간에 구동 0 을 보낸 뒤 조종권을 돌려준다.
  조향은 누를 때의 목표에 머문다. 버튼을 놓거나, 창이 포커스를 잃거나, 화면이 가려지거나, 화면의 hold 신호가 0.4 s 끊기면 바로 구동 0 이다.
  STOP 은 언제나 이긴다(서버가 이동을 끝내고 브리지가 조종권을 거둔다). 끝난 뒤 2 s 안에 화면이 조종권을 가져가지 않으면 STOP.
  이동 중에는 화면 자신의 구동·keepalive 요청을 서버가 409(`distance_move_running`)로 막는다. 브리지의 구동 상한(`max_pwm`)과 펌웨어 구동 감시는
  그대로이고, duty 의 PWM 이 상한보다 크면(표의 속도가 나오지 않음) 또는 상한이 0 이면 시작하지 않는다. ESP32-S3 조향 브리지에서만 된다. 앞으로만(v1).
- **한계.** 10월 차의 값이라 처음 몇 번은 짧은 거리로 줄자 확인부터 한다. 출발은 88~100 % 에서만 쟀고, 낮은 duty 의 출발 지연은 가정이다.
  3dba62c 부터 ESP32 브리지가 구동을 서서히 켜고 끈다(출발은 PWM 60 으로 뛰고 약 150 PWM/s 로 오름, 끝의 구동 0 은 약 320 PWM/s 로 내림; 예: 40 %(PWM 102)는
  오름 약 0.3 s·내림 약 0.3 s, 100 %(PWM 255)는 오름 약 1.3 s·내림 약 0.8 s). 계획 식의 L·C 는 옛 차의 값이고 이 램프를 따로 넣지 않았다. 램프 몫이
  속도마다 달라 한 속도에서 잰 배율이 다른 속도에 그대로 맞지 않으므로 보정을 속도별로 쌓는다: 새 속도는 한 번 줄자로 재어 넣는다. 보간한 속도는
  10월 기록에도 없는 값이다. 속도 눈금 자체가 참조끼리 3~10 % 다르다. LiDAR 로 거리를 닫는 제어는 다음 판(v2)이다.

### 1-7. 2026-11-18 현장 문제와 고친 것

- **배터리 교체 뒤 `steer_profile_required`.** 보드·브리지가 다시 켜지는 동안 화면이 차동 조종판을 띄웠고, 그 조종 활성화(vehicle_profile 없음)를 조향
  브리지가 거절했다. 이제 화면은 한 번 본 조향 브리지를 이 브라우저에 기억해(`ubts-vehicle-kind-seen`) 다음에 열 때 바로 조향 패널을 쓰고, 차동 조종판으로
  저절로 돌아가지 않는다. 서버는 vehicle_profile 없는 조종 활성화를 조향 브리지로 보내지 않고 한국어 까닭과 profile 을 돌려주며, 화면은 그때 조향 패널로 바꾼다.
- **가변저항 값 무효(배선 확인).** 가변저항이 4095 로 붙는 접촉 불량(2026-11-18 발견)이면 브리지가 `pot_invalid` 로 조향·조종 활성화를 막는다(맞는 동작).
  조향 패널은 그동안 조종 활성화 버튼을 끄고 "가변저항 값 무효(배선 확인)"을 보인다. 보드가 다시 연결 중이면 "보드 다시 연결 중"을 보인다.
- **조종 활성화가 꺼진 까닭 기록.** 브리지가 arm, disarm(까닭: `input_expired`, `stale_input`, `page_status_stale`, `page_hidden`, `device_unavailable`,
  `pot_invalid`, ...), 보드 연결 변화, 준비 안 됨 까닭 변화를 남긴다. 상태의 `control_events`(최근 10개), 파일 `rover_control_events.jsonl`(상태 파일 옆,
  최근 1000줄, 환경 변수 `ROVER_CONTROL_EVENT_LOG`). 같은 사건은 2 s 에 한 번. 조종자 세션은 적지 않는다.
- **A/D 조향 속도.** 조향 패널의 'A/D 조향 속도'(3~20 °/s, 이 브라우저에 저장). 20 은 지금처럼 끝 목표를 한 번에(바퀴 자체 속도). 더 낮으면 누르는 동안 목표가
  그 속도로 움직인다. 바퀴보다 느린 목표는 SMOOTH 펌웨어가 짧게 가고 서기를 되풀이할 수 있다(가짜 보드 성질, 차에서 재지 않음).
- **끌기 막대.** 브리지 `ANGLE` 간격 0.2 → 0.1 s, 화면 0.1 → 0.05 s. 바퀴 최고 조향 속도(PWM_MAX 80 에서 약 19 °/s, 바퀴 든 상태 측정)보다 빨리 끌면
  목표(파랑)와 측정(검정) 막대의 차이로 늦음이 보인다.
- **휴대폰에 남은 상태(2026-11-18: 그 휴대폰만 계속 실패, 새 PC 브라우저는 됨).** 쪽(HTML)은 이제 `Cache-Control: no-store`(새 판을 늘 받는다,
  판 번호 붙은 파일은 그대로 오래 저장), API 는 원래 no-store. 같은 이름의 세션 쿠키가 여럿 오면(옛 쿠키) 서버가 아는 것을 쓴다. 조향 패널의
  '화면 초기화' 버튼: STOP → 서버 세션 지움(`POST /api/session/reset`, 쿠키 만료) → 이 브라우저의 저장 값 지움 → 다시 불러오기. 조종권(lease)은
  원래 브라우저에 저장하지 않는다. 서버 판이 바뀔 때 저장 값을 저절로 지우는 판 번호 확인은 넣지 않았다(초기화 버튼으로 대신).
- **아직 안 한 것(제안).** 짧은 연결 끊김에도 조종 활성화를 남기는 설계(구동은 바로 0, lease 는 몇 초 유지, 다시 누를 때만 다시 감, 응답이 사라진 요청의
  재동기화)는 안전 규칙을 바꾸는 일이라 이번에 넣지 않았다. 지금 시간 예산: 화면은 상태가 1 s 오래되면 STOP, 브리지는 구동 입력 0.75 s·입력표 1.5 s·
  보드 STATUS 0.6 s 가 끊기면 정지·해제, 펌웨어 구동 감시 0.3 s. 휴대폰·터널에서 응답이 1 s 넘게 늦으면 조종 활성화가 꺼진다. 다음 현장의 사건 기록으로
  어느 길이 많은지 보고 정한다. 조향 최대 속도(SM PWM_MAX)를 화면에서 바꾸는 것도 제안으로 남긴다.

## 2. 옛 ESP8266 (차동 V2, ~2026-11-16)

`rover_control_test`의 `UBTS_WHEEL_PWM_V2`와 WheelController를 사용한다. 기존 WAVE ROVER UART/HTTP 프록시와 파일 명령 경로는 폐기했다.

### 연결 구조

브라우저 → Dashboard 자동 세션 → `/run/ubts-rover/control.sock` → `ros2-esp-rover-bridge` → 고정 USB ESP → 모터.

ESP 브리지만 모터 포트를 연다. LiDAR와 ESP는 같은 USB VID/PID를 사용하므로 장치 이름이나 CP210 자동 탐색으로 구분하지 않는다. Compose가 서로 다른 by-id 장치를 매핑하고 ESP는 실제 udev ID_SERIAL도 확인한다. flock과 TIOCEXCL로 중복 소유를 차단한다. 기존 Tk 테스트 프로그램을 쓸 때는 ESP 브리지를 먼저 중지하고, 테스트 프로그램을 완전히 종료한 후 다시 시작한다.

ROS에는 `/rover/status`, `/rover/control/requested`, `/rover/control/applied`를 발행한다. `/cmd_vel`은 구독하지 않는다. 수동 조종 종료 후 자동 주행으로 넘어가지 않는다. `applied`는 MCU의 PWM 피드백이며 엔코더 속도가 아니다.

왼쪽 방향 D8/D5, 오른쪽 방향 D3/D0, 전원 D1/D2/D6/D7 매핑을 유지한다. 정상 입력 해제는 MCU 가감속, STOP/Esc/창 이탈/통신 만료는 즉시 정지를 요청한다. MCU의 전원 핀 유지 정책도 기존 펌웨어와 같다. 웹 STOP은 물리 전원 차단 장치가 아니다.

### 사용

1. `/rover-control`에서 **조종 활성화 OFF**를 눌러 ON으로 바꾼다. 별도 조종 암호는 없다. 다시 누르면 정지하며 OFF가 된다.
2. WASD 또는 방향 버튼을 누르는 동안 이동한다. 한글 입력 모드에서도 물리 WASD 키를 사용한다.
3. W+A / W+D / S+A / S+D는 이동하면서 좌·우로 꺾는다. 안쪽 바퀴는 설정 속도를 유지하고 바깥쪽은 1.5배, 최대 100%다. 속도 100%에서는 바깥쪽을 더 높일 수 없어 대각선도 직진한다.
4. 슬라이더는 주행 중에도 바로 반영된다. Q는 −5, E는 +5 퍼센트 포인트이며 한 번 누를 때 한 단계만 바뀐다. 길게 눌러 자동 반복하지 않는다. 조종 패널을 숨기거나 속도 슬라이더에 포커스가 있어도 WASD/Q/E는 작동한다.
5. STOP/Esc 또는 창 이탈 시 조종권이 해제된다. 재접속으로 자동 활성화되지 않는다.

속도 30%의 좌/우 요청: W=30/30, A=−30/30, S=−30/−30, D=30/−30, WA=30/45, WD=45/30, SA=−30/−45, SD=−45/−30. 후진 A/D는 후진 경로가 좌/우로 휘는 방향이다. W→WA→W 및 속도 변경 시 별도 정지 명령을 끼워 넣지 않으며 V2 MCU의 기존 가감속을 따른다. 응답 대기 중 입력 변경은 최신 상태만 유지하고 응답 직후 전송한다.

대시보드를 연 브라우저에 세션을 자동 생성하며 별도 입력은 필요 없다. 조종권은 한 세션만 소유한다. 연속 입력에는 일회용 티켓과 순번을 적용한다. 입력 0.75초 만료, 티켓 1.5초 만료, 유휴 조종권 30초 만료다. keepalive는 이동 유효 시간을 늘리지 않는다. MCU watchdog 2초가 호스트 정지에 대비한다. 너무 느린 망에서는 정지 후 재활성화가 필요하며 안전 시간을 늘리지 않는다.

### 저속 전송

전송 품질의 자동 모드는 작은 프레임부터 시작해 수신 확인 시간에 따라 조절한다. 카메라와 LiDAR는 각 연결에서 하나의 미확인 프레임만 허용한다. 응답이 없으면 연결을 닫고 오래된 프레임을 쌓지 않는다.

| 모드 | 카메라 최대 크기/FPS/JPEG 품질 | 카메라 목표 상한 | LiDAR 표시 |
|---|---|---|---|
| 극저속 (64 kbps) | 160×90 / 2 / 30 | 3 KB/s | 최대 60점, 1 Hz |
| 매우 느린 망 | 320×180 / 4 / 40 | 30 KB/s | 최대 180점, 3 Hz |
| 균형 | 640×360 / 10 / 55 | 120 KB/s | 최대 450점, 5 Hz |
| 고화질 | 1280×720 / 15 / 70 | 400 KB/s | 원본 설정 이내, 10 Hz |

종횡비를 유지하고 작은 입력은 확대하지 않는다. 예산은 애플리케이션 메시지 기준이며 TCP/TLS·상태 정보·IMU 트래픽은 별도다. 실제 회선이 느리면 수신 확인이 FPS를 더 낮춘다. 느린 모드에서는 라이브 AI 오버레이를 생략한다. ROS 원본, AI 입력, 녹화 원본에는 이 축소를 적용하지 않는다. LiDAR는 극좌표 배열로 전송하고 브라우저에서 표시 좌표를 복원한다.

자동 모드는 극저속에서 시작한다. 극저속에서는 IMU 표시 1 Hz, 전체 텔레메트리 조회 10초 간격을 적용해 영상 외 트래픽도 줄인다. 선택한 프로필은 화면 미리보기에만 적용된다. 64 kbps는 목표 회선 예산이며 가용 대역폭이나 지연 보장은 아니다.

### AP와 설치

관리 AP는 `band=bg`, 채널 6, 절전 비활성화로 유지한다. 현재 인터넷에 연결한 station의 5GHz 사용과 AP의 2.4GHz 설정은 별개다. 프로필 검증은 기존 프로필의 대역도 확인하며 활성 AP를 원격으로 강제 변경하지 않는다. 2.4GHz 자체가 특정 거리를 보장하지 않으며 안테나·장애물·간섭에 따른 현장 시험이 필요하다.

배포 전 코드와 Compose, 이미지 ID를 백업한다. 레거시 `unist-orachard-ros2-rover-bridge`는 restart=no로 바꾸고 중지한 뒤 새 브리지를 실행한다. ESP는 disarmed 상태로 시작하고 V2 펌웨어를 확인하기 전 조종을 허용하지 않는다. 잘못된 장치 또는 장치 분리 후에는 고장 상태를 유지한다. 장치를 확인하고 컨테이너를 다시 생성해야 한다. USB 재연결로 장치 번호가 달라져도 다른 USB 장치를 자동 선택하지 않는다.

단위 테스트는 가짜 모터 및 로컬 WebSocket에서 수행한다. 정지 상태 실장비 확인과 실제 주행·거리 시험은 별도로 기록한다.
